Running a five-agent AI financial planner in production

Alex is a multi-agent SaaS: users model their investment accounts, then a team of cooperating AI agents classifies holdings, writes a portfolio report, builds charts and runs retirement projections. An autonomous research agent browses the web on a schedule to keep a vector knowledge base current. I deployed, debugged and operated every layer on AWS, and re-engineered the parts that broke under real conditions.

01 The system

A user signs in with Clerk, adds accounts and positions, and asks for an analysis. The request goes onto a queue so the API returns immediately. A Planner agent picks it up, refreshes live prices from Polygon.io and calls four specialists as tools:

  • Tagger classifies each instrument by asset class, region and sector.
  • Reporter writes the portfolio report, drawing on the research knowledge base, and is scored by a separate judge.
  • Charter produces chart data for the dashboard.
  • Retirement combines LLM reasoning with a 500-run Monte Carlo simulation.

Every result is written back to the jobs table. job_id is the correlation key across the queue, the agents, the database and the traces.

02 Architecture

Fully serverless and event-driven. Nothing runs, and little is billed, until a user asks for an analysis or the research schedule fires.

Frontend & API

  • Next.js 15, React 19, TypeScript and Tailwind 4, exported statically to S3 and CloudFront
  • FastAPI on Lambda (Mangum) with ~17 endpoints and per-resource ownership checks
  • Clerk JWTs validated against the JWKS endpoint on every request

Async orchestration

  • SQS decouples the API from long agent runs
  • Dead-letter queue after 3 failed receives
  • Planner sized at 15 min / 2 GB, specialists at 5 min / 1 GB

Data & retrieval

  • Aurora Serverless v2 over the RDS Data API, so Lambdas need no VPC
  • Shared repository-style database library used by every agent and the API
  • S3 Vectors as a low-cost alternative to OpenSearch for semantic search

Security

  • Least-privilege IAM role per service
  • Secrets Manager for generated database credentials
  • API-key and usage-plan protection on the ingest API; S3 public-access blocks and encryption

03 AI engineering

Multi-agent orchestration

  • Orchestrator–specialist pattern on the OpenAI Agents SDK: the Planner calls specialists as tools, each in its own Lambda
  • Typed dataclass run contexts pass job_id and user_id into tools without leaking them into prompts
  • Explicit max_turns budget per agent to bound every loop
  • Mock-Lambda mode runs the whole orchestration locally with no AWS calls

Structured outputs vs tool calling

  • A hard rule that each agent uses one or the other, never both, working around a real LiteLLM + Bedrock limitation
  • Tagger returns a validated Pydantic schema (gt=0, allocation breakdowns by asset class, region and sector)
  • Reporter, Charter and Retirement call tools against the database and the vector store

LLM-as-a-judge quality gate

  • A separate Judge agent scores every report 0–100 through a structured Evaluation model
  • Scores attached to LangFuse spans for review
  • Reports below the quality threshold are flagged and rejected

MCP agent & RAG

  • Researcher drives headless Chromium through the Playwright MCP server, containerised on App Runner
  • HuggingFace all-MiniLM-L6-v2 on a SageMaker Serverless endpoint, concurrency tuned to the account quota
  • Ingestion and semantic search on Amazon S3 Vectors, read by the Reporter during analysis

04 Production problems I solved

These changes go beyond the base code and come from my own commit history.

Provider-portable LLM routing

  • Diagnosed a production blocker: Bedrock on-demand token quotas were effectively zero in every region tested (us-east-1, us-west-2, eu-central-1), and filed a quota increase
  • Rather than wait, removed the hard-coded bedrock/ prefix from all five agents and the Judge
  • Model strings now come fully from config, and LiteLLM routes to OpenAI or Bedrock; existing env var names kept so deployed infrastructure needed no change
  • Verified afterwards: 5/5 local agent tests, 5/5 deployed-Lambda tests, and the full pipeline in ~74s

Bounding a runaway agent

  • The researcher ignored soft limits ("1–2 pages MAX"), ran 13+ turns, hit 60s Playwright timeouts on cookie walls and pushed past App Runner's 120s limit
  • Rewrote the prompt as hard, countable rules: at most 1 navigate, 1 snapshot, exactly 1 ingest, no retries, at most 4 tool calls
  • Switched to a plain-HTML source, cut max_turns to 8 and raised MCP timeouts from 60s to 180s for cold starts
  • Found Chromium alone needs ~1.5 GB and scaled App Runner from 1 vCPU / 2 GB to 2 vCPU / 4 GB, ending the navigation timeouts

Guardrails & explainability

  • Output guardrail: a validator checks LLM-generated chart JSON before it is saved, with required fields per chart type, so malformed output fails fast instead of reaching the UI
  • Schema-enforced reasoning: a rationale field declared before the allocation fields, so the model explains itself before it commits to numbers
  • Rationales logged to CloudWatch and traced in LangFuse for audit

Builds & operations

  • Fixed a macOS x86_64 build failure (no prebuilt fastuuid wheel) by moving heavy agent dependencies into an optional uv group installed only inside Docker
  • Lambdas built against the Lambda runtime image so native dependencies match the target
  • One-command deploy and destroy scripts, plus a written runbook with cost-aware teardown (Aurora flagged as the main cost driver)

05 Engineering judgement

Reason about context windows

A Playwright MCP page snapshot can return 20–50k tokens, which overflows a 128k context within a few turns. I chose gpt-4.1-mini for its 1M-token context at low cost, and only tool-capable models for MCP work.

Design for vendor portability

Cross-region inference profiles, per-region model access and Bedrock's model availability by region are real constraints. When the provider was unavailable, the system moved to another one without changing any infrastructure.

Rules, not suggestions

Agents treat soft guidance as optional. Countable limits, turn budgets and timeouts turned unpredictable agent behaviour into bounded, predictable execution.

Cost as a design input

S3 Vectors instead of OpenSearch, serverless inference for embeddings, scale-to-zero compute, and teardown scripts that remove each stack in dependency order.

06 Testing & observability

  • Agent tests run locally with mocked Lambda calls, then again against the deployed Lambdas.
  • End-to-end test resets the database, puts a job on SQS and polls up to 5 minutes for a completed report.
  • Load and infrastructure tests cover scale, multiple accounts, Aurora Data API connectivity and S3 Vectors ingest and search.
  • LangFuse tracing via Logfire instrumentation captures every agent run, tool call and judge score, flushed explicitly at the end of each Lambda invocation.
  • Two CloudWatch dashboards, AI model usage and agent performance, provisioned with Terraform, plus a local tool that streams live logs from every agent during a run.
  • Exponential-backoff retries with tenacity on LLM rate-limit errors.
