01 The problem

LOUD's backend, 16 Spring Boot microservices with MySQL, MongoDB, Redis, Kafka and Consul, ran on AWS for about $5,000 a month. For a startup at LOUD's stage, that was out of line with its traffic. The estate had also drifted:

  • "Production" ran on the staging Spring profile.
  • Every database shared one EC2 host in us-east-1, far from an African user base.
  • Deploys were hand-rolled SSH/SCP scripts copying JARs onto systemd units.

02 Audit first, then recommend

I audited the code and the live AWS account instead of relying on existing documents. The audit overturned a key assumption: the "managed" RDS, ElastiCache and MSK services didn't exist. Everything was self-hosted on a single EC2 instance, so the company was paying AWS prices without getting the benefits of managed services. That changed the business case. I evaluated four options:

Option 1

Optimise in place

CloudFront and Global Accelerator in front of the existing ALB.

Faster, but no cheaper.

Option 2

Lift and shift to af-south-1

Move the same estate closer to users.

Same cost model, same operational burden.

Option 3

Re-platform to ECS Fargate

Containers on a managed AWS runtime.

More managed, but more expensive.

Recommended

Leave AWS for dedicated cloud VPS

Contabo servers, with the operational gap filled by automation.

Accepted by management: −95% cost.

03 Target architecture

A 5-node, hybrid active-active design: 46 vCPU and 170 GB RAM in total. Redundancy goes where the blast radius is largest (the gateway and config server), and the data tier is reachable only over the private network.

Edge

  • Cloudflare DNS and Load Balancer with gateway health checks on both app nodes
  • Unhealthy node removed automatically
  • Measured distribution of 13 / 17 across 30 requests

App tier

  • Nginx terminates TLS (Let's Encrypt via Cloudflare DNS-01)
  • Gateway and config server run on both nodes
  • 13 domain services split by domain affinity, routed across nodes via Consul

Data & storage

  • Databases on a node with no public IP and no Nginx
  • MinIO replaces S3; its admin console is never exposed
  • Health-gated startup and exporters for MySQL, MongoDB and Redis

Documented trade-offs

  • Single-node DB, storage and monitoring, kept for cost
  • Hybrid active-active instead of full duplication on both nodes
  • Accepted in writing by the business as part of a risk register

04 How I delivered it

Discovery to a live public endpoint took about 10 days (11 to 20 September 2026). Observability, CI/CD and hardening continued into October.

  1. Discovery and audit. Baselines of row, document and object counts; Kafka, Consul and S3 sizing; an inventory of every AWS dependency in the code.
  2. Hardening. Base role, private-IP verification, UFW default-deny, key-only SSH, fail2ban and named admin accounts.
  3. Secrets. Rotated every credential and moved secrets to Ansible Vault and Spring Cloud Config {cipher} values.
  4. Stateful infrastructure and monitoring. Pinned image versions, health-gated startup, database exporters.
  5. Object storage. MinIO deployed and seeded; eight services' S3 clients re-pointed and proven by reading production objects back byte for byte.
  6. App services. Moved from JARs under systemd to Docker Compose, deployed one host at a time with port and health checks.
  7. Data migration. Dumps, restores and count reconciliation (41 MySQL tables, 37 MongoDB collections), with a test-restored backup before each step.
  8. Cutover. Cloudflare load balancing on the public API, plus a compatibility path (wildcard certificate and an Nginx staging- → prod- rewrite) so already installed mobile apps kept working during store review.
  9. Operate. CI/CD, central logging, external probes, dashboards, and a written handover to the frontend team.

05 What I built and fixed

Infrastructure as code & CI/CD

  • 13 idempotent Ansible roles: hardening, private networking, Docker, UFW, Nginx, Let's Encrypt, databases, MinIO, monitoring, logging, app services
  • 6 Ansible Vault-encrypted secret stores
  • GitHub Actions → Ansible pipeline: mandatory --check --diff dry run, then a separate approved apply
  • Rolling deploys (serial: 1), a concurrency lock and post-deploy verification
  • Human approval gate kept without paying for GitHub Team/Enterprise
  • Retired the legacy SSH/SCP deploy pipeline

Security

  • Found production running on test configuration and live payments pointed at the provider's sandbox
  • Removed plaintext credentials from source, including an AWS access key in 7 places, and rotated every database and storage credential
  • Found that Docker-published ports bypass UFW, exposing databases; bound every port to loopback or the private IP
  • Closed public actuator and metrics endpoints on 12 services
  • Stopped an active brute-force campaign (339 SSH attempts in 10 minutes) with key-only SSH, fail2ban and per-engineer sudo accounts

Observability

  • Prometheus, Grafana, node_exporter and database exporters
  • blackbox_exporter for external uptime and TLS-expiry probes
  • Grafana Alloy and Loki for central logging
  • Docker log rotation on every host
  • Dashboards and datasources provisioned as code

Production incident

  • An Android home-screen crash after go-live, fixed within hours
  • Traced to a JPA entity with 19 eager collections and 20 MB base64 images stored in JSON rows
  • Users' JSON data went from ~68 MB to ~17 KB
  • A lazy-loading refactor cut SQL statements per user load from 761 to 1

06 Engineering judgement

Verify, don't assume

Every claim was checked against the live system: external port scans, JWT tests (no token, valid, expired, wrongly signed, under-privileged) on 6 services on both nodes, measured load balancing, and byte-for-byte object comparisons.

Ship safely without staging

With no staging tier, safety came from enforced dry runs, serialised rollouts and post-apply checks, not from pretending a staging tier existed.

Remove hidden risk

I reconciled 287 production commits the migration branch was missing, so recent features like Apple sign-in and a wallet fix weren't silently lost.

Documentation as a deliverable

A ~26,500-word migration record, a plain-English executive summary, architecture docs with diagrams, logging and alerting designs, a post-migration backlog and a cross-team handover.

07 What's next

A migration isn't finished at cutover. These items were open when this case study was written, and I've listed them as designed or planned rather than done:

  • Alert routing: rules are designed and waiting on a Slack contact point.
  • Automated daily backups: restores were tested by hand at every step; scheduling is next.
  • Container image builds in CI: images are currently built on the host.
